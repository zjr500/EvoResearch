本文件记录 EvoResearch 插件的数据库、运行环境、依赖版本与向量检索方案，与《接口契约与数据库设计》v1.2 同步迭代：表中已确定的内容不得随意修改，确需修改时四名成员同步确认并记录；未列出的依赖允许后续按需补充。

## 1. 运行环境

- **插件运行侧**：Node.js `>=22.19.0`（建议使用受支持的 Node.js 22.x LTS 或满足条件的更新版本）。插件是 ESM 格式的 npm 包，装入 DSH 客户端运行，不独立部署服务端。
- **DSH 开发基线**：0.2.1-rc.2（第 1 周最小可行性验证后锁定）。插件声明兼容该版本，每周例会检查上游变更日志。
- **远程执行侧**：用户自备 GPU 服务器，经 SSH 接入（复用 DSH 官方 SSH provider，凭证由 DSH/OpenSSH 管理，插件不落库）。远程机器的 Python 版本、显卡、驱动、深度学习框架不做预先约定，登记主机时由环境自检确认并记录（POST /remote/hosts/check）。

## 2. 数据库：SQLite（better-sqlite3）

**结论**：插件本地数据库用 SQLite，Node 侧驱动用 better-sqlite3。第二章设计的 13 张表全部建在这一个库文件里。

**理由**：

1. 插件随用户机器本地运行，不能要求用户另外安装和运维一个数据库服务；
2. 13 张表、单用户规模，数据量小，SQLite 的能力足够；
3. 支持事务，能满足幂等记录、执行意图先落库再下发这类"先写后做"的要求；
4. 整个库是一个文件，备份、迁移、排查问题都简单。

## 3. 向量检索：sqlite-vec

**结论**：不引入独立的向量数据库，用 sqlite-vec（SQLite 扩展）在同一个库里做向量近邻检索。

**做法**：kb_entries.embedding 字段存向量本体，配套 sqlite-vec 虚拟表做相似度检索；POST /kb/search 按余弦相似度取 topK；条目更新或删除时同步重建索引——接口文档里 PUT/DELETE 条目时说的"索引重建、索引失效"就是这一步。

**理由**：

1. 向量条数与知识条目数同级（课程规模几百到几千条），轻量索引足够，用不上独立向量数据库；
2. 向量与业务数据同库，归属过滤、测试集过滤可以直接写在同一条查询的条件里——如果用独立向量库，"这个用户能不能看到这条结果"的过滤逻辑就得拆到两个组件里做，容易漏；
3. 不增加安装组件，插件安装链路不变。

**Embedding 模型**：使用 DeepSeek 开放平台或兼容 OpenAI 协议的 Embedding 接口（与立项报告"模型资源"一节一致），向量维度以所选模型为准，建库时按维度固定。

## 5. 版本迭代补充（v1.1，2026年11月18日）

### 5.1 Node.js 版本下限

将插件运行侧下限统一为 **Node.js `>=22.19.0`**。原因是当前选用的 `better-sqlite3@13.2.0` 要求 Node.js `>=22.19.0`；仅写 Node.js ≥20 会允许安装到不满足原生模块运行要求的环境。开发机、CI 与验收环境应统一使用 Node.js `>=22.19.0`，并提交 lockfile，避免依赖解析漂移。

### 5.2 数据库迁移与字段变更

接口/数据库 v1.1 增补 `optimization_direction`、`seed_count`、运行启动失败状态及图谱异步作业状态等字段。实现时必须提供可重复执行的数据库迁移，已有数据应设置合理默认值（例如 `optimization_direction=maximize`，但仅适用于原有指标语义明确为越大越好的任务；语义不明的历史任务应标记待确认，不可静默套用默认值）。

### 5.3 本地验收最低要求

- 使用 Node.js `>=22.19.0` 安装依赖并执行插件构建；
- 验证 better-sqlite3 与 sqlite-vec 在目标操作系统上的加载、建表、事务、向量写入与检索；
- 从空库执行全部迁移，再从 v1.0 数据库副本升级到 v1.1；
- 验证任务启动幂等、远程启动状态不确定时的恢复检查、终止确认、认证中断后部分结果保留；
- 验证 `GET /kb/entries`、`GET /graph/nodes/{nodeId}`、任务草稿重新校验及预警规则参数校验。
