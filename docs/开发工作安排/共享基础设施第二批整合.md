## 实际实现

### 认证与 HTTP

- `src/infrastructure/http.ts` 统一调用 DSH `connection.admit(request)`；保留 DSH 自己的认证、Host/Origin 检查及凭证管理，不读取密钥或另建登录系统。
- 固定版本 `dsh-typert-protocol/lib/types/types.d.ts` 的 `PrincipalMap.owner` 只有 `kind: 'owner'`，没有多用户 ID。因此仍将本机宿主 owner 映射为已有数据库 owner 1。其他 principal 拒绝，客户端字段不能指定资源归属。没有声称实现多租户身份映射或测试集 Agent 权限。
- 公共能力包含认证前置、请求大小上限、JSON 对象校验、客户端归属字段拒绝、正整数安全 ID、`{code,message,data}` 响应与未知异常脱敏。
- 认证失败仍保持 HTTP 401/403，超限为 413；这些原本为空的错误响应现在也有 JSON 外壳，沿用参数/访问错误码 4001。业务成功/受理、404、400、500 行为保持。
- F1/F2 现有 `/papers`、`/kb` 路径及 `/kb/operations/{id}` 查询继续可用。未新增业务路由、未接入前端或 F12。

### 操作记录与迁移

- `operation_records` 统一记录元数据：`id/idempotency_key/operation_type/target_id/status/request_digest/result_ref/created_at/updated_at`。
- `operation_payloads` 为基础设施结果与归属存储：`operation_id/owner_id/scope/client_key/result_json/error_code/error_message`。操作主表不直接保存业务结果正文，`result_ref` 指向对应 payload。
- `knowledge_operations` 不删除。旧记录按原 ID、摘要、状态、结果、错误和时间迁移；之后知识库服务通过同一短事务同步兼容副本。新任务也保留旧表可读性。
- 当前唯一写入口为 `OperationService`，`knowledge/Operations` 只保留兼容外观。其他模块以后使用不同 scope；不能继续绕过服务直接写旧表。
- 新迁移文件 `migrations/shared/001_operations.sql`，登记 `operations:1`。原知识库 SQL 不改动。旧库若已有未登记的公共操作表、未知版本或 ID 冲突，整体回滚并拒绝覆盖，不重新编号。
- 迁移与操作认领使用 SQLite IMMEDIATE 短事务，避免多连接先读后写竞争；模型调用和其他工作在事务外进行。

### 幂等与恢复

- 唯一作用域为 `(owner_id, scope, client_key)`。主表的全局唯一 `idempotency_key` 保存该三元组的 SHA-256，客户端原键保存在 payload 中；不改变 F1/F2 请求字段。
- 相同作用域和内容返回原操作 ID/结果；相同键不同内容返回 4020。不同用户或模块互不占用键。
- 知识库沿用历史 digest 算法，包含原有路径与输入；其他模块的公共服务还把 target_id 纳入摘要。旧记录的 target_id 不推断补写。
- 只有成功持久化新认领的调用会执行 work。失败和成功记录都不会因相同键重试而再次执行；两个独立进程竞争同一键已测试。
- 重启恢复仅把不可恢复的本地任务标记失败，不自动重放。知识库兼容入口保留启动恢复行为；同一进程中的第二个服务实例不会把仍活跃的任务误判中断。
- **部署边界：同一数据库只运行一个 DSH 宿主。** 跨进程认领测试不代表支持多个活跃宿主同时做启动恢复；未引入分布式租约。
- 数据库提交和外部副作用无法组成一个原子事务；不能声称任意崩溃情况下“恰好一次”。用户改用新键可能重新付费，恢复提示要求人工判断，不能自动换键重试。未来训练执行还需稳定 execution_id 和 DSH jobs 的恢复适配，本批未开发实验执行。
